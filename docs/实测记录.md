# 实测记录

这是作者一个人、一台 Mac 上，2026 年 9 月底到 10-10 的真实使用记录。**不是对照实验**：没有拿同一个任务分别在「有 Harness」和「没 Harness」下各跑一遍。这里的结论是观察，样本也不大。

时间要分开看：核心协议 AGENTS 是作者在日常使用里迭代了约三个月的结果（作者自述）；精简成现在的 Harness 之后，只实测了几天（Claude Code 从 10-06 傍晚起，DSH 和 Codex 从 10-08 起，到 10-10 为止）。

## 2. 行为指标

**口径**
- **回合**：两条用户消息之间的全部记录。
- **多步回合**：工具调用 ≥5 的回合。
- **阶段预告**：文字里出现「第 N 步」「第 N/M 步」「共 N 步」。
- **三件套**：写或改 `方案.md`、`TODO.md`、`交接.md`，包括用命令行改写（`sed -i`、`cat >>` 之类）。
- **先查后动**：回合里第一次用写文件工具之前，有几次工具调用。

全部是文本规则匹配，是粗口径。Codex 的工具是一段段 JS，读和写分不开，所以它的「三件套」和「先查后动」两列更粗。

**修正说明**：第一轮漏计了两类写入，「写三件套」和「先查后动」两列已按第二轮的脚本改过。
- 漏掉的第一类，是 Claude 和 DSH 用命令行改三件套（抽查 16 条，都是真写入）。
- 漏掉的第二类，是 DSH flash「只有 AGENTS」期里大写的 `Edit`/`Write` 工具调用。
- 第一轮原值：三件套 Claude 36% / 77% / 28%，DSH flash 7%，中转 Opus 61%；DSH flash「只有 AGENTS」期的先查后动是 7。
- 两轮的回合切分略有差别（第二轮把后台通知触发的续跑并进上一回合），多步回合数相差不到 4%。
- Codex 几行仍是第一轮的值。

**怎么读**

- **条款一写进去，三家都出现了对应的行为。** 阶段预告是 10-05 才加进协议的，「方案 / TODO / 交接」三件套是重型期加的。Codex 和 DSH flash 换上精简 Harness 后，这两项都大幅上升。这里模型和软件没换，换的是 Qlimen：核心协议，加上私有协议和钩子，不只是协议正文。精简期样本小：Codex 主会话 19 个回合、DSH flash 9 个回合，按会话单位各只有 4 个。要打个折扣：「第 N 步」这种说法在阶段预告条款加入之前就有，Claude 10-05 以前的多步回合里约 20% 命中（30/153），其中一部分只是在说清单里的步骤。
- **DeepSeek flash 的「先查后动」从 3 涨到 13。** 补上漏计的写入以后，「只有 AGENTS」期的中位数从 7 降到 3，前后差距比第一轮算的更大。但精简期只有 9 个写过文件的回合。作者的原话是：以前「边想边做」，现在「先想清楚」，错了也只是小步来回，不再大起大落。
- **按回合算，Claude 在重型期各项最高，精简后回落，多数项和「只有 AGENTS」期相近。** 这里比的是每回合出现的频率。重型期只有 26 个回合，22 个多步回合里 14 个来自同一个会话，所以主要反映的是那一个会话。按会话单位看（下文「按会话统计」），精简期的三件套、阶段预告、末尾交代、耗时说明都看不出回落；但重型期只有 3 个单位，两种口径都比不出高低。作者和 Opus 都认为重型期是负担：指标高不等于好用，文书量和任务大小不成比例。
- **副作用**：Codex 被别的模型当工人跑的时候，也读了全局协议，于是开始写状态标记和阶段预告，其实工人用不着。精简期 15 个工人会话里，还有 6 个自己写了方案、TODO 或交接，用的是 Python 写入，表里的规则只识别出一部分。waibao 派出的 kimi 工人不读全局协议（2026-10-05 冒烟确认），没有这个问题。
- **样本小**：DSH flash 精简期只有 9 个回合，Codex 精简期主会话只有 19 个回合。

### 按会话统计

上面的表按回合算，Claude 精简期写三件套只有 57%（第一轮漏计时只有 28%）。这个数偏低，主要是被稀释了：Claude 一个会话往往很长，三件套在任务开头建一次，之后在同一个会话里反复更新。按回合算，没写三件套的回合大多是在已有三件套的任务里接着干活，或者只是回答问题。

按回合统计测的是「协议动作出现的频率」，不等于「遵守程度」。一个只回答问题的回合本来就不该写三件套；反过来，Codex 工人回回写阶段预告，频率很高，其实是多余的。按会话统计回答的是「这段工作里这个行为有没有出现」，同样不等于遵守：写过一次三件套，不代表后来一直在更新。两种口径都只能看格式，看不到判断对不对。

| 模型调用 | 165 | 1414 |
| 工具调用 | 193.5 | 1565 |
| 上下文压缩次数 | 0 | 4 |
| 首尾跨度（小时） | 3.75 | 284.2 |

- 模型调用 ≥300 次的会话有 13 个，压缩过的有 11 个。作者说的「一个会话几百轮」，按模型调用算成立；按用户发言算是几十轮。
- 对照：DSH 会话的用户回合中位 9、最大 32；Codex 中位 1、最大 26。
- 三件套「建一次、持续更新」也有数据：写过三件套的单位，三件套中位写了 14～23 次（Claude 三个阶段）；Claude 写过三件套的 45 个任务目录，每个中位写 8 次、最多 60 次，只有 3 个被两个以上会话写过。基本是一个任务一个长会话。

**口径**
- **单位**：一个会话在一个阶段里的那一段。只算含至少一个多步回合的单位。
- **写过三件套、阶段预告、至少一次……**：单位里出现过一次就算，再除以单位数。阶段预告「窄」同上表；「宽」另外算上「第一步」「步骤 N：」「第 N/M 项」这类写法。
- **末尾交代**：回合里最后一次工具调用之后的文字，说清了「在等你」、「后台在跑 / 没在跑」，或者「我接着做 / 收工」。「全末段」在这段文字里任意位置找；「末两行」只看最后两行，最严。先算每个单位自己的交代率，再对单位取平均，长会话不会压过短会话。
- **耗时说明**：说过预计多久，或者说明这段时间插不了话。这一列也把「用了约 3 分钟」这种事后说法算进去了；「先说耗时再动手」只算说完还有工具调用、而且不是过去式的那种。

**怎么读**

1. **稀释是真的，Claude 上最明显。** Claude 精简期写三件套，按回合 57%，按单位 91%；阶段预告按回合 34%，按单位 83%。DSH 中转 Opus 的阶段预告也差得多（按回合 38%，按单位 89%）。Codex 主会话的会话短，两种口径差得不多。
2. **回合末交代状态、说明耗时，在 Claude 里普遍存在。** 这两项上一版没纳入统计。回合末说清在等谁、后台跑不跑，Claude 三期都约 100%，最严的「末两行」口径也有 87%～98%。至少说过一次耗时或「插不了话」的单位，「只有 AGENTS」期 100%、精简期 87%，重型期 3 个单位里有 2 个（67%）；这一列含「用了约 3 分钟」这类事后说法。更严的「先说耗时再动手」是 67%～77%。作者说「经常看到」，数据支持。
3. **Claude 的这些行为只能写「稳定存在、与条款一致」，算不清有多少是 Harness 的功劳。** Claude 没有无协议的对照期，「只有 AGENTS」期本身就带着协议，分不清有多少是 Opus 本来的习惯。
4. **同模型前后对比最干净的是 Codex 主会话。** 从无协议到精简：三件套 10% → 75%，末尾交代 14% → 90%，阶段预告 0% → 75%；至少一次耗时说明（含事后说法）29% → 75%，先说耗时再动手 19% → 75%。但精简期只有 4 个单位，只能说方向一致，不能当定量。
5. **模型能力占了很大一块。** 协议相近时，Opus（Claude、DSH 中转 Opus）各项在 67%～100%，多数在 80% 以上（4 行 28 格里 19 格），偏低的集中在「先说耗时再动手」和只有 3 个单位的重型期；DSH flash「只有 AGENTS」期是 13%～72%。DSH flash 换到精简后，三件套 47% → 100%，阶段预告 20% → 50%，末尾交代 72% → 75% 基本没变，至少一次耗时说明 40% → 0%，先说耗时再动手 13% → 0%。精简期只有 4 个单位，有升有降，说明不了更多。
6. **副作用也更明显了。** Codex 当工人时，精简期 77% 的单位写阶段预告，67% 在末尾写「在等 / 后台」，可工人根本没人在等。

**这一节的局限**：全靠正则，抽查了 34 条，没做系统的准确率和召回率；「你再试一下看看」这类暗示式收尾不算交代，对 Codex 偏保守。只评了每个用户回合最后的结尾，Claude 回合中途停下来等后台通知的那些点没单独评。各阶段做的任务不一样，阶段间的差异里混着任务差异。

## 3. 具体片段

都对过会话原文，时间是作者的本地时间。

1. **Codex 接入后的第一个任务（10-08）。** 18:55:35 开始「第 1/6 步」，依次是：
   1. 先核官方文档；
   2. 方案、TODO、交接落盘；
   3. 核实私有协议已经注入、钩子已经被信任；
   4. 用无害的 `echo` 测 guard；
   5. 跑免费的 `waibao --status`：沙箱挡住了，它请用户批准在沙箱外运行，没有自己绕；
   6. 收尾。

   作者截图上记的是 3 分 41 秒。作者的感想：「有点 opus 的感觉了」。
2. **「解锁」不等于「批准」（10-08）。** 作者为了让 Opus 改受保护的文件，解锁了 29 个路径。Opus 回的是：「解锁收到。你没回挂不挂 DSH 注入，这一项我先不动，只做已经批准的那几件」。
3. **重型制度碍事的一晚（10-08 晚上）。** 作者想让 K3 一次跑几个小时，「特批一次跑完」。但派工脚本单次最多 10 分钟，工人档案又只读，Opus 只能请作者在终端里自己启动 K3。
   - 启动失败两次后，Opus 按协议停下来，等作者决定。
   - 它想把失败经过写进交接，写文字也被 guard 当成启动模型拦了。它没有改写法绕过去，而是请作者定。
   - 作者：「那我要先解决制度了」。第二天把规则改了：预算只提醒、不拦；guard 从「拦」改成「问」；K3 可以用 `--out` 写结果文件夹。
4. **压缩以后接着干（10-10）。** 一个图文排版任务的上下文用到 1M 窗口的九成左右时被自动压缩，一次压掉约 85.7 万 tokens。压缩后的第一句是「接着修，先看交接停点」：先改正了交接里写错的日期，再修上次停下的那一处，4 分钟后修好。作者平时的做法是说「交接」，然后手动压缩或开新会话，「任务无缝交接」。交接文件降低的是换会话、压缩后的接续成本，它自己也会写错（这次就错了日期），接手的人仍要核对现状。
5. **整理季度信息（10-10）。** Opus 没有直接生成本季度的表，先找到上季度的算法和口径，用同一个脚本复刻上季度的表做回归测试，对上了才开始。作者：「我都没打开过表格软件」。作者印象里，另一个模型以前做同类任务时，要作者一格一格教口径；这不是同协议、同任务的对照。
6. **从零写一个新游戏的日常脚本（10-07）。** 一个会话约 80 分钟：自己摸界面、打一轮、发现结束条件不对就改、离线验证、实测、更新日志。
7. **让 Opus 评估 Harness（10-06）。** 依据是 38 条派工账本和 5 份复盘，评估的结论如下：
   - 跨对话连续性（交接、TODO、记忆）收益最大；
   - K3 交叉审查第二，一次 10 条意见 8 条成立，另一次 16 条采纳 12 条；
   - 38 次派工里有 25 次是 Harness 在测自己；
   - 大任务上收益大于负担，小任务上是负担，要先减重。

   作者当天就砍掉了约 80%。
8. **中转站的教训（10-09 排查）。** 同一个模型名下，中转站至少换过三种来源，其中一种 0 缓存、不返回思考内容。所以 DSH 里「中转 Opus」的表现不能代表 Opus，第 2 节那几行只当参考。
9. **同一个会话，接协议前后怎么花额度（Codex，10-08 → 10-10）。** 这个会话用一个第三方付费接口取资料。
   - 10-08 下午还没接核心协议。作者让它把几个信息源一起整理，它直接取回了 99 份正文，回报「没有权限或额度失败」。
   - 10-10 同一会话已经接上精简协议。要补一份简报时，它先说明这一步要「消耗……1次通用API额度，不另调用付费模型」，再问「你批准这一次列表查询吗？」，最后写「目前已停下等待回复，没有后台任务在跑」。

   模型、软件、接口都没变，多出来的是「先报花费、逐笔请示」这一步（核心协议第 3 节）。10-08 那次读多少，本来就在作者的要求范围内，不算越权。
10. **失败两次就停，换路先问（Codex，10-08 晚上）。** 接上核心协议当天晚上，Codex 要读几篇在线文档。浏览器只读总览连续两次超时，它停下，请作者给链接。之后又碰上三条路连续超时，第一次它写的是：「我已按协议停下，不做第三次重试，也不改用坐标点击去绕」。

## 5. 归因：哪些是 Harness 的功劳

Qlimen 不赋予模型新能力，而是通过诚实、授权、验证、状态管理和交接这些通用规则，约束执行过程：先查、落盘、请示、如实标出没验证的、交付前核对。所以「能力来源」不等于「结果贡献」。能力来源问的是「谁有本事做成」，结果贡献问的是「哪些因素促成了这个结果」。只看能力来源，协议的间接作用会全被记成零；只看结果，又会把模型的聪明算到协议头上。

上一版正是前一种偏差：把「协议里没直接写这个行为」当成了「Harness 没帮助」，把「关键词没搜到」写成了「没有证据」。这一版分四类：

- **直接贡献**：行为能对上具体条款，而且有同模型前后变化、不同模型同协议都出现，或者会话原文里模型自己说明是按协议做的。
- **可能的间接贡献**：协议没写这个具体做法，但诚实、核实、授权、落盘这些通用规则可能促成了它。没做对照实验，只能说「可能」。
- **模型主导**：协议里没有对应条款，能力明显来自模型。
- **已知局限或负面影响**：协议没防住的、碍事的、带来副作用的，包括这份评估本身的偏差。

用到的三条判据：
1. 协议里有没有对应条款；
2. 同一个模型换了 Harness 前后有没有变化；
3. 不同模型在同一套 Harness 下是不是都表现出来了。

**一句话**：Harness 管得住「怎么干活」：先调研、先落盘、分步说、批准要明确、出错就停、没验证的说没验证。它不给模型新本事，但会通过这些执行方式间接影响结果，影响多大，这份记录量不出来。

## 6. 局限

- **时间和样本**：一个人、一台电脑。核心协议 AGENTS 是约三个月里踩坑迭代出来的；精简版 Harness 只实测了几天，精简期的样本小（DSH flash 9 个回合，Codex 主会话 19 个回合）。
- **不是对照实验**：Claude 没有无协议的基线，各阶段做的任务也不一样，阶段差异里混着任务差异。
- **自动统计有盲区**：正则擅长数明确的格式行为（状态标记、三件套、阶段预告），对需要理解上下文的协议遵守情况覆盖不足，比如该不该停、批准是否明确、有没有越权。「没搜到」不等于「没发生」。
- **来源有偏**：作者的观察来自和 ChatGPT 的聊天，带主观色彩；中转站模型来源不稳定，相关数据只当参考。
