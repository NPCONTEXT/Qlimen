# 设计取舍：从重到轻

> 一句话：Qlimen 曾在两三天里长成一套「流程 + 手册 + 钩子 + 派工制度」的重型 Harness。让 Opus 拿派工账本自评之后，作者砍掉了约 80%，只留下四样：核心协议、各环境私有协议、兜底安全、工人名册。本文讲砍了什么、为什么砍、留下什么、停用件怎么放回、哪些代价是明知的。

核心协议每一条的来历另见 [协议来历.md](协议来历.md)。

## 1. 结论先行

- 真正起作用的，是一份写清「用户要什么、什么不能做」的核心协议，加上方案、TODO、交接三件套带来的跨会话连续性。
- 外面那一圈流程、手册、执法钩子，在大任务上有收益，在小任务上是负担，而且会自我繁殖：为了维护或绕开一条制度，又长出一套新制度。
- 作者的总结：做再多制度和拦截，不如在核心协议的「第一优先级写上诚实」（作者复盘原话）。
- 停用的东西不删，原样收在 `archive/`。放回的标准只有一条：出了问题，并且能指认某个停用件本来能拦住它。

## 2. 经过

| 时间 | 发生了什么 |
|---|---|
| 10-05 之前 | 只有一份核心协议 AGENTS。作者说里面的条款基本是「一个坑一个坑」踩出来的，坑多来自 DeepSeek 和 Kimi |
| 10-05～10-06 | 围绕 AGENTS 长出重型 Harness：流程 skill（定级、模板、验收关卡）、5 本作业手册、4 个钩子、工人分工和派工路由、预算拦截、更宽的加锁范围 |
| 10-06 下午 | 让官方 Opus 依据 38 条派工账本、5 份 Harness 任务复盘评估：这套东西对它是帮助大还是限制大 |
| 10-06 傍晚 | 作者拍板瘦身。方案改了五版（v1–v5），当晚落地 |
| 10-08 | 停用件从原位挪进 `archive/`，免得被当成在用的东西 |
| 10-08～10-09 | 瘦身后又松了两处留下的底座：预算改成只提醒、guard 改成弹框问用户（见第 8 节） |

## 3. 为什么砍

**结论**：Opus 的评估是「大型、跨多次对话的任务，收益大于负担；小任务上是负担；而且得先减重」。作者的判断更狠：之前提升大的，基本只靠 AGENTS 就够了。

评估里被证明有用的（出处：10-06 评估，依据 38 条派工账本和 5 份复盘）：
- **跨对话连续性**（交接、TODO、记忆、复盘）收益最大。Opus 每次对话都从零开始，这些文件就是它的长期记忆。
- **换一家模型审查**（K3）排第二：审 Harness 方案 4 次，每次都抓到真问题；一次 10 条意见 8 条成立，另一次 16 条采纳 12 条。
- **机械验收**有效：有一次改文档弄坏了旧任务的验收项，是回合结束时被钩子拦下才发现的。
- **便宜模型通读长文**（DeepSeek flash）适用面窄但有用：约 24 万 tokens 没进主模型上下文，花 ¥1.11，88 条结果没有一条编造。

被证明是负担的（同一出处）：
- **Harness 在测自己**：38 次派工里 25 次是 Harness 在测自己，约三分之二。
- **文书量和任务大小脱钩**：一次小修补只改了 46 行代码，却生成了 12 个文件和目录。
- **同一条规则写在好几处**：协议正文、入口文件、记忆、skill 里都有，写法慢慢不一致；有一次返工，就是两处的定级标准互相矛盾。
- **规则之间打架**：协议要求「被纠正就当场写入」，又把这些文件锁了，结果每个任务攒一个「待落盘」目录，评估时已有 4 个散在各处。
- **旧验收项反咬**：做完的任务，验收项照样被检查，改任何文档前都得手动搜一遍旧方案。
- **派工选项比用到的多**：规则写「先派 k28，不够再升 K3」，可 k28 的 7 次记录全是冒烟测试，真实审查都直接派了 K3；让 flash 替主模型看截图，属于「管它比自己做还累」，为打通这条路还失败过 3 次。

作者自己的观察（10-06 讨论和 10-10 复盘，转述）：
- 三天的演化已经到了「过分纠正」的程度，还出现了为维护或绕开一个制度、衍生出一整套额外制度的情况。
- Opus 一个人能兜住四五个模型的活，结果还要花额外时间等 K3 的反馈。
- 发散和收敛本来就是做产品的两个阶段；收敛之后，任务落盘、交接、TODO、踩坑复盘、多模型会审这些仍然在实用。

**一个「制度生制度」的实例**（出自归档钩子的源码注释）：收尾验收钩子 `finish-check` 原来扫整个工作区，会拿别的会话刚锁定的方案来拦本会话；于是加了 `track` 钩子按会话记「动过哪些任务目录」；又因为每个回合都拦、太频繁，改成「任务看起来做完了才查」「同一组失败项最多拦 2 次」；再加一个「已归档」标记文件，让旧任务不再被查。每一步都合理，加起来是一整套只为维护验收而存在的机制。

## 4. 分层标准

**结论**：每条东西先问「它写的是谁的事」，再决定放哪。这条标准只在设计时用，不写进协议。

| 这条东西写的是…… | 放哪 | 例子 |
|---|---|---|
| 用户要什么、什么不能做 | 核心协议 `core/rules/AGENTS.md` | 中文、诚实、授权、花费、三件套 |
| 这个模型在这个壳里怎么做到：能力、缺陷、习惯、本机的坑 | 该环境的私有协议 | 能不能看图、后台跑完会不会叫醒、压缩后协议还在不在 |
| 某个工人会什么、多少钱、怎么叫 | 工人名册 `core/skills/waibao` | K3 审查要 41–484 秒、读不到加锁文件 |

用户是同一个人，换哪个模型，核心都成立；壳和模型换了，私有协议跟着换；工人换了，只改名册。

**反例**：「看图派工人」是给没有视觉能力的、经中转站接入的 Opus 定的，却写进了全局分工表；官方 Opus 能自己看图，接手后只好在全局再补一条例外。按新分法，这条只出现在那个环境的私有协议里。

**差点分错的两处**：
- 「>60 秒放后台、前台 ≤90 秒、不 sleep 轮询」，方案 v1 当成 Claude Code 的特性挪去私有。作者指出这几条是 DeepSeek 实际犯过错才写的；Opus 查自己的历史会话，2358 次前台命令里 19 次超过 90 秒。它写的是用户要什么（插话插得进来、不被假进度骗），v2 留回核心。
- 反过来，核心里原有一句「后台任务完成会自动通知并触发后续」，只对 Claude Code 成立（会话记录里实测 47 次），而 DeepSeek 时期的记录是「通知不等于叫醒」。v3 把核心改回中性写法，「会不会叫醒」交给各环境私有协议。

## 5. 砍掉了什么

**结论**：停用，不删除。每一件的要点，要么并进了核心里的一句话，要么挪进了名册，要么确认没人需要。

| 部件 | 原来做什么 | 为什么停 | 要点去了哪 |
|---|---|---|---|
| 流程 skill `qlimen-flow` | 定级 L0–L3、方案 / 交接 / 验收模板、工人分工表 | 文书量跟任务大小脱钩；定级标准和别处打架 | 「方案写什么」「交接写清什么」各并成核心里的一句；工人事实进名册，派工路由删掉 |
| 5 本作业手册（数据、游戏、Harness、音视频、网站） | 各类任务的调研清单和坑 | 只在对应类型的任务里有用，常驻是负担 | 原文在 `archive/`；私有协议里留一句「做到对应类型时可以翻」 |
| 每轮提示钩子 `intake`（Claude 侧） | 每轮附一段「先分清评价还是需求」 | Claude Code 压缩后会从磁盘重新加载项目入口和记忆，不必每轮提醒 | 「只问看法就只回答」原话并进核心 §1。DSH 侧保留：那边协议会被压缩压掉，它是唯一的每轮提醒 |
| `track` + `finish-check` 钩子 | 记本会话动过的任务目录；回合结束时跑验收、催写交接 | 见第 3 节的「制度生制度」 | 核心 §6「每个要用户审批的节点都按交付对待」 |
| `verify` 关卡 | 方案锁定前、交付前机器检查验收清单 | 跟着流程 skill 一起失去用处 | 先降为可选工具，10-08 随其他停用件进 `archive/` |
| 派工路由 | 「先派 k28，不够再升 K3」 | k28 真实任务 0 次；路由逼主模型做多余的判断 | 名册只记事实，派不派、派谁由主模型自己定 |
| flash 看截图（全局） | 让便宜模型替主模型看图 | Opus 自己能看图；界面好坏没法用脚本核对，最后还得复看 | 只留在没有视觉的环境的私有协议里 |
| 强制复盘 | 每个任务写 `复盘.md` | 小任务不值得 | 不再强制；该记的坑写进私有协议或记忆 |
| K3 前置审查 | 定级 L2 以上，方案先过 K3 再给用户 | 主线串行等待 | 改成第二审查，见第 7 节 |

瘦身过程中提出、又撤掉的两样，也算在「砍掉」里：
- **本机记录层**（v3 新增，v5 删）：一份记代理、硬件、本机坑的共用文件。作者说那是 DeepSeek 怕再把电脑搞坏自己加的；核心 §2 已要求每次写清资源占用，由用户判断就行；代理能现查，其余几条已在 Opus 的记忆里。
- **「审批点」小节**（v2 新增，v4 删）：为 K3 列了高风险清单、回滚、等待条件。作者指出又复杂了，这是在用新规则补规则。

## 6. 留下的四样

| 部件 | 在哪 | 谁维护 | 加锁 |
|---|---|---|---|
| 核心协议 | `core/rules/AGENTS.md`，约 10 KB，基本保持原文 | 主模型出 diff，用户批准 | 锁 |
| 各环境私有协议 | 每个环境一份，示例在 `examples/私有协议/` | 该环境的主模型；用户纠正当场写 | 不锁 |
| 兜底安全 | `guard` 钩子；`qlimen-lock` / `qlimen-unlock` 加锁；派工脚本 `core/workers/waibao`（账本、预算提醒、工人默认只读、越界记录） | 用户批准才改 | 锁 |
| 工人名册 | `core/skills/waibao`，只记带日期和来源的事实 | 主模型 | 不锁 |

核心协议的举证责任是反的：它是作者一个坑一个坑写出来、只靠它就已经见效的部分，所以默认保留原文，只动和停用部件挂钩的句子，并补回旧版里丢掉、仍然有用的半句。加锁范围同时收窄：瘦身前一次解锁是 83 个路径，瘦身当晚收到 27 个（出处：作者环境里加解锁命令的输出）。

## 7. 两个关键改动

### 7.1 K3：从前置审批员到并行质检员，再到一句话

**结论**：K3 不再是关卡，而是作者的第二审查。派了就后台跑，不等它；意见由主模型核实后转告作者，作者来定。

演变经过（都在 10-06 当天）：
1. 重型期：定级 L2 以上的方案要先过 K3 审查，主模型只能等。
2. 讨论中提出「把 K3 从前置审批员改成并行质检员」：审查放后台，等的时候做不依赖审查结论的事。Opus 的初版还留了三种必须等 K3 的情况（动权限或安全边界、不可逆操作、架构定型）。
3. 作者改成把 K3「当成我的第二审核员」：等她的时候直接做更多工作，她的意见留着，和作者的意见汇合后再执行。
4. Opus 的 v2 又加了「审批点」小节：高风险清单、必须写回滚、必须等 K3 和用户都到齐。
5. 作者叫停：本意是精简、不干扰，快慢是 K3 自己的事，「没赶上就算了」。v4 删掉整节，只剩核心 §2 的一句话。

为什么这样最省：高风险操作本来就要用户批准（核心 §3），最终把关的是用户，不需要再加一道门；K3 的意见交到用户手里，等它的时间被用户读方案的时间盖住；晚到的意见照常转告，不另写规则。

考虑过、没选的：只让 K3 审交付物、不审方案（方案级硬伤会拖到交付才暴露）；换更快的 k28 当审核员（它没有审查实绩）。为了让 K3 快一点，名册里写了提速办法：只给方案和关键文件，要它「最多列 N 条最重要的」。账本里 K3 审查用时 41–484 秒，慢的都是让它读了很多文件。

10-10 开源审核时又定了一条：审核员用外部视角，不套核心协议。作者的理由是，审核的核心是「给一段信息，判断对不对」，套上协议可能受限；只读这类安全边界由工具配置保证（waibao 的工人档案、Codex 的只读沙箱），不靠协议。K3 经 waibao 的工人模式本来就不读全局协议，只带一页工人守则；这次另用一个只放登录凭据、不带协议和 skill 的 Codex 做外部审稿（做法见 [core/skills/waibao/外部审稿.md](../core/skills/waibao/外部审稿.md)），15 条意见里抓到几个此前没发现的代码问题：guard 漏判双引号里的命令替换、撤销命令不校验路径等，已修。核心 §2 因此补了一句；同一轮意见还指出 §7 把权限错误一概当成加锁，也改了（见 [协议来历.md](协议来历.md) §7）。

### 7.2 私有协议不加锁

**结论**：核心和安全机制加锁，私有协议不锁。否则被纠正之后没法当场写。

核心 §6 要求「用户纠正的每个点须当场写入」，§7 又把规则文件锁了。重型期的结果是：每次被纠正只能先记进一个「待落盘」目录，等用户下次解锁再一起写，评估时已经攒了 4 个。私有协议放开以后，学到就能写；属于核心的纠正，仍然出 diff、等用户解锁。

代价也写在这里：私有协议成了新的长胖点。信号是里面开始出现「必须先……再……」这种流程句，那就是官僚又开始长了。

## 8. 明知的代价

瘦身时就写下的：
- **收尾验收没了**。`finish-check` 抓到过一次改坏旧任务验收项的问题。现在靠核心 §6 的自查；不经审批节点的小改动没有兜底，和重型期的 L0 小改动一样。
- **DSH 没人催交接**。DSH 自动压缩用内置的英文摘要、不读交接，影响比 Claude 大。由 DSH 的私有协议补一句「交接要勤写」。
- **前台限时只靠文字**。DeepSeek 时期 DSH 有钩子硬拦前台超过 90 秒的命令，换壳后只剩文字，Opus 照样犯了 19 次。给 guard 加这条拦截，当时定为瘦身落地后单独决定；本仓库版本的 guard 里没有这一条。
- **名册几个环境共用**，写错会误导别的模型，所以只记带日期和来源的事实。

瘦身之后才发现的：
- **预算和安全被放进了同一格**。瘦身方案把预算拦截和 guard 一起写成「安全底座：不动」。10-08 作者特批一次长任务，派工脚本的 10 分钟硬上限照拦，只能让作者在终端直接启动 K3；写文字时又被 guard 误拦。作者的反应是先解决制度。10-09 改成：预算只记账、只提醒，用户批准高于预算；guard 从直接拦改成弹框问用户；K3 可以写进指定的结果文件夹跑长任务。教训：写限制时分清是安全边界还是默认预算。
- **核心协议对工人也生效**。行为统计里，加载了全局协议的 Codex 工人也开始给状态标记和阶段预告，这些工人其实用不着（10-10 统计，正则粗口径）。
- **记忆是提醒，不是闸门**。路径写法、zsh 变量这类坑写进了记忆，照样反复犯。

## 9. 恢复的标准

**结论**：出了问题，并且能指认「某个停用件本来能拦住它」，才放回那一件，而且只放那一件。

- 不按「感觉少了点什么」放回，也不整套恢复。
- 放回方法见 [archive/说明.md](../archive/说明.md)：文件挪回原位，重新挂载（skill 建链接、钩子写回配置），连带它引用的模板一起放回。
- 截至 2026-10-10，作者环境的钩子挂载和 skill 列表里都没有停用件，没有放回过任何一件。
- 同一标准也反过来用于留下的部件：留下的底座碍事了照样松，10-09 的预算和 guard 就是例子。

## 10. 没验证的

- 前后对比都是观察，不是同一个任务的对照实验。10-06 评估里真实任务的证据只有两块，其余都是 Harness 修 Harness。
- 「砍掉约 80%」是作者的估计，不是按文件数或行数算的。
- 经中转站接入的 Opus 来源不稳定（同一个模型名下至少换过三种来源），它在重型期的表现不能代表 Opus。
- 行为统计（10-10）用正则从会话记录里数；部分环境精简期样本很小（DSH flash 9 个回合、Codex 主会话 19 个回合）。
